# 数据模型

## 边界

系统只保留两个边界：

- **基础库**：跨旅行复用的成员资料与标签。
- **Trip**：一次旅行及其日程、地点、交通、预订、费用、物品和资料。

地点属于旅行，不进入基础库。展示名称不能作为外键，所有关系使用不可变 ID。

每条 Trip 资源记录都包含 `id`、`tripId`、`resource`、`recordKey`、`position`、
`version`、`createdByMemberId`、`updatedByMemberId`、`createdAt`、`updatedAt` 和经
资源规则校验的 `data`。`resource` 标识 Day、Place、Segment 等资源类型；内部
`groupKey` 只用于分组排序，不进入 API 或快照。

`createdByMemberId` 固定记录创建成员，`updatedByMemberId` 记录最近一次修改的发起成员；
事务内的自动联动沿用发起这次业务操作的成员。两者都是当前记录元数据并进入完整快照，
不能替代只追加的操作记录。

## 成员与身份

`members` 是唯一人员主数据。成员 ID 同时用于登录身份、会话、管理员校验、旅行权限、
费用和物品归属；不存在独立用户业务实体。

成员保存姓名、可选的 11 位手机号、备用联系方式、紧急联系人联系方式、管理员标记、
状态和备注。手机号全局唯一；成员拥有登录凭据时手机号必填，并作为唯一登录标识，不再
存在自定义登录名称。密码哈希放在以同一成员 ID 为键的私有凭据集合，不进入成员记录、
业务快照或日志。成员修改自己的手机号或密码时必须验证当前密码，但已有 Session 保持
有效，不要求重新登录。成员状态显式改为 `inactive` 时，服务端在同一事务中删除其全部
Session；新登录和后续每次 Session 校验也都拒绝该成员。状态未提供时按启用处理。
仍是未删除旅行 owner 的成员不能停用；在提供受控的负责人转移入口前，系统必须保留
owner 连续性。
某次旅行的 `members` 资源只选择基础成员 ID 并保存旅行角色；新旅行的创建成员直接成为
owner。
删除旅行成员前必须检查其作为预订人、费用付款人、费用分摊成员、资料记录人和个人物品
所有人的引用，并返回可见资料的名称与引用关系。手工费用可在明确确认后连带删除；与预订
绑定的自动费用必须跟随预订处理，不能单独级联。预订和资料引用仍是阻塞项，必须先人工修改。
其他成员的个人物品不返回名称或数量，只说明存在私有依赖。阻塞项清空后，删除请求可以
显式确认连带删除该成员在当前 Trip 中的全部手工费用和个人物品；成员关系、费用、物品、
非负责人访问权、审计和完整快照必须在同一事务完成。未显式确认时仍拒绝删除；删除事务会
重新检查全部引用，避免预览后的并发写入留下悬空成员关系。
删除基础成员时还要列出其作为旅行成员、预订人、费用付款人、费用分摊成员、资料记录人
和历史操作者的具体位置；个人物品在同一旅行内只折叠显示一项匿名依赖。仍是任何旅行
owner 或存在业务引用的成员不能物理删除。已停用、没有业务引用且不再是旅行 owner 的成员，
可以在管理员明确确认后于同一事务中注销登录凭据、删除全部 Session 和基础成员；历史操作
记录继续作为历史信息保留。启用中的登录成员必须先停用，不能一步跳过停用确认。

Trip 删除采用逻辑删除：只写入 `deletedAt`、`deletedByMemberId` 并递增修订号。被删除旅行
不再出现在旅行列表，也不能通过普通业务接口访问；其 Day、Place、Segment、预订、费用、
物品、成员关系、操作记录和快照均保留，不做级联物理删除。旅行 owner 与管理员可以执行
删除；管理员也可以导出完整备份，但这两项管理能力不会赋予查看或编辑旅行内容的权限。

## 标签

`tags` 只有四种分类：

- `general`：通用标记。
- `place-type`：地点类型。
- `expense-type`：费用类型。
- `platform-type`：预订和资料的来源平台。

地点的 `type` 必须引用一个 `place-type` 标签；预订和费用的 `type` 必须引用同一套
`expense-type` 标签；预订与资料的 `platformId` 必须引用一个 `platform-type` 标签。
新基础库除平台类型外，还预设常用的地点与费用类型；现有基础库由管理员显式执行
“补充常用类型”，在一个事务中只增加缺失项。删除被引用标签前必须列出影响，管理员确认
后把引用替换为同分类的“其他”标签，
再删除原标签；正在充当兜底项的“其他”标签不能以自己替换自己。删除影响必须包含逻辑
删除旅行中仍保留的资料，并明确旅行、资料类型、资料名称和引用关系，不能把这类引用
误报为资料不存在。被旅行资料引用的标签不能跨分类修改，避免当前聚合生成无法恢复的
快照。

同一分类内的标签名称忽略大小写后必须唯一；名称在写入前去除首尾空白。不同分类可以
使用相同名称，但不能互相映射。

## Trip

Trip 是聚合根。持久字段为 `id`、`title`、`summary`、`startDate`、`endDate`、
`timezone`、`currency`、`version`、`createdAt` 和 `updatedAt`；逻辑删除后再保存
`deletedAt`、`deletedByMemberId`。`summary` 是可留空的旅行概述。列表响应中的
`role` 是当前成员的权限投影，不进入 Trip、快照或备份。

日期范围最多包含 366 个自然日。创建 Trip 时，服务端在同一事务中为起止日期内的每个
自然日生成一条标题为“待规划”的 Day，并连同 owner 权限、操作记录和初始完整快照一次
提交。所有后续业务写入同样必须在事务内校验、提升 Trip 修订号并生成完整快照。

### Day

Day 直接保存当天的地点顺序：

```json
{
  "title": "车站到景区",
  "date": "2026-09-30",
  "placeEntries": [
    {
      "placeId": "place-a",
      "arrivalTime": "09:00",
      "departureTime": "10:00",
      "additionalInfo": "到站后取车"
    }
  ],
  "additionalInfo": "当天需要留意的自由文本"
}
```

`date` 在 Trip 内唯一并位于日期范围内。`placeEntries` 中地点不得重复；D1、D2 只由
日期顺序计算。Day 不保存进度、天气城市、天气行政区代码、最晚出发或硬截止。天气由
当天关联地点的 `weatherAdcode` 动态组成列表。

`placeEntries` 的最低有效内容只有 `placeId`。数组顺序表示建议游览顺序，不代表实际
执行进度；到达时间、离开时间和补充信息均为可选线索。缺少时间是正常状态，页面不得据此
提示计划未完成，也不得根据当前时钟推断用户位于哪个地点。

### Place

```json
{
  "name": "示例观景点",
  "type": "place-type-tag-id",
  "address": "示例省示例市山景路 1 号",
  "region": "示例市",
  "longitude": 120.1001,
  "latitude": 30.1001,
  "weatherAdcode": "110101",
  "navigationURL": "https://uri.amap.com/...",
  "openingHours": "08:00-18:00",
  "recommendedTicketPlatform": "官方小程序"
}
```

地点位置通过高德搜索或地图落点确认。来源链接、联系说明、电话、官方来源、状态、
时间约束、重要程度、补充信息和多标签都不属于地点。开放时间无法稳定从高德获得时由
用户填写。

修改地点前列出关联执行日。确认删除后，地点会从 Day 移除，关联 Segment 会删除，
预订与资料保留但解除地点关联；整个过程在一个事务中提交。

从某个 Day 的“新增地点”入口创建 Place 时，Place 创建与追加到该 Day 的
`placeEntries` 必须在一个事务中完成，只提升一次 Trip 修订号并生成一份完整快照，不得
留下已创建但未关联的中间状态。

### Segment

交通段直接连接同一个 Day 内的两个地点：

```json
{
  "dayId": "day-id",
  "fromPlaceId": "place-a",
  "toPlaceId": "place-b",
  "mode": "drive",
  "departureTime": "09:00",
  "durationMinutes": 150,
  "distanceMeters": 210000,
  "navigationURL": "",
  "additionalInfo": "天黑前走完山路"
}
```

交通方式可为步行、自驾、出租车、网约车、公交、火车、飞机、接驳车、景区交通、轮渡、
自行车或其他。起终点必须都在该 Day 的 `placeEntries` 中。

Segment 整体是可选的路线参考，不是 Day 完整性的前提。创建 Segment 时必须选择起点、
终点和交通方式；出发时间、预计时长、距离、导航链接和补充信息均可留空。

### Booking

预订保存项目、预订类型 `type`、预订人 `bookerMemberId`、可选地点、可选平台类型、
日期/时间、状态、订单链接和备注。预订类型直接引用费用类型标签；预订人必须是当前旅行
成员。预订不保存金额、分摊或地点描述，也不关联日程或交通段。

每条预订在同一事务中自动创建一条待登记费用。费用项目、费用类型和支付人分别强制跟随
预订的项目、预订类型和预订人；无论修改预订还是直接调用费用接口，都不能让这三个字段
与来源预订分离。发生时间、金额和分摊在费用中维护。预订页面显示费用缺失项并可直接打开
对应费用；自动费用不能手动删除，删除预订时自动删除。

### Expense

费用保存 `item`、精确到分钟的 `occurredAt`、费用类型标签 `type`、最小货币单位
`amountMinor`、支付成员、分摊方式和成员快照。

- 手工费用不能关联预订。
- `splitMode=selected` 时由用户选择成员。
- `splitMode=all` 时服务端保存当前全部旅行成员的基础成员 ID 快照。
- 不保存重要程度或结算状态。旅程结算由支付金额与应分摊金额实时计算，输出成员净额和
  建议转账。

预订自动费用允许暂缺金额；支付人始终由预订人同步，补录金额后参与结算。

### PackingItem

物品属于 `Trip + 基础成员`。`ownerMemberId` 由当前登录成员强制写入；查询、详情、修改
和删除都在服务端按该成员过滤。日程关联物品也必须调用同一个受权限保护的物品接口。

物品只保存名称、类别、关联执行日、数量、`packed` 和备注；不保存使用日期、额外状态、
重要程度或必要程度。

### ResearchEvidence、旅行成员与用餐

- `research-evidence` 只保存标题、内容、平台类型、记录成员，以及可选的关联执行日和
  地点。列表可按执行日和地点筛选；地点可按类型和关联日期筛选，预订可按类型和预订人
  筛选，费用可按类型筛选。
- Trip 内 `members` 选择基础成员并保存旅行角色和备注。
- 用餐支出统一使用费用类型“三餐”。

## 操作记录

所有业务写操作在同一事务中写入 `audit_logs`：操作者成员 ID、时间、模块、动作、记录、
修改前和修改后。包括自动预订费用、标签兜底替换、排序、快照恢复和快照导入。记录只
追加，不进入 Trip 快照，避免恢复旧数据抹除审计历史。

资源记录上的 `createdByMemberId`、`updatedByMemberId` 回答“谁创建、谁最近修改”，会
随当前记录进入快照；`audit_logs` 回答“每次操作发生了什么”，只追加且不会被恢复覆盖。

Trip 操作记录接口不混入基础库的全局操作。物品操作仍完整保存在内部审计中，但接口只
向 `ownerMemberId` 对应的当前成员返回；不包含 owner 的聚合排序记录默认隐藏。

## 快照

Trip 快照直接使用当前数据结构，包含：

```text
days, places, segments, bookings, expenses,
packing-items, research-evidence, members
```

基础库快照同样直接使用当前数据结构，只包含 `members` 和 `tags`。

完整 Trip 快照和可移植旅行备份会包含所有成员的物品。这是完整恢复与管理员灾备的明确
例外，不等同于普通业务查询权限：快照列表、下载、恢复预览和恢复只允许旅行 owner，
可移植备份只允许旅行 owner 或管理员导出，editor 与 viewer 均不可访问这些完整载荷。
内部快照和镜像仍保持完整，不因 HTTP 授权投影而删减；后续若扩大访问范围，必须先设计
成员维度的物品投影与可合并恢复语义。

数据库内的 Trip 与基础库快照都按创建时间建立查询索引，并按
`mirror_state + created_at` 建立待镜像扫描索引。文件镜像不是事务提交条件：失败时状态
保持 `pending`，后台任务持续补偿；镜像成功后再标记为 `mirrored`。

## MongoDB 物理契约

`repository.Initialize` 是 API 启动时的数据库契约安装入口，不负责导入攻略或重置数据。
它集中管理当前模型的集合 validator、索引和模型指纹：

- 业务集合使用 `validationLevel=strict`、`validationAction=error`，顶层及各资源 `data`
  均拒绝未声明字段。
- 安装前先只读检查全部已有文档；任一文档不符合当前模型时直接停止，不做任何写入或
  删除。
- 唯一索引保护稳定键、排序位置、手机号、标签分类名称、成员关系和幂等键；TTL 索引
  清理过期 Session 与幂等请求。出现未受管索引时启动失败，不会擅自删除。
- `library_state.reference_epoch` 是不进入接口和快照的内部并发闸门。Trip 业务事务在
  校验外部引用并生成完整快照时与基础库写入共同递增它，使“新增引用”与“修改或删除
  被引用资料”发生事务写冲突并自动重试，避免两个各自合法的并发事务组合成悬空引用。
  只读旅行备份使用 snapshot read concern 获得跨集合一致视图，不递增此闸门，也不会
  把 GET 导出变成数据库写入。
- validator 与受管索引共同生成 SHA-256 指纹。全部安装成功后才把指纹写入
  `system_metadata/current-model`，健康检查必须与代码内指纹一致。

结构变化因此必须先用当前完整快照在一次性副本集演练。不能绕过启动失败直接执行
`collMod`、关闭 validator 或在服务器手改不符合当前契约的文档。

## 旅行备份与导入

旅行总看板可把一个 Trip 的当前完整业务状态导出为
`kind: my-travel-trip-backup` 的 JSON。备份包包含 Trip 快照以及这次旅行实际引用的
基础成员、标签描述，但不包含登录凭据、管理员身份、Session、幂等记录、历史快照或
历史操作记录。

导入始终创建新 Trip，不覆盖已有旅行。服务端为 Trip 和全部旅行内记录重新分配 ID，
重写日程、地点、交通、预订和费用等关联，并把版本、时间和操作者重置为新旅行状态。
基础成员按 ID 映射，标签可按 ID 或“分类 + 名称”匹配；缺失项不会自动创建，界面会
明确询问是否随导入创建。只有管理员确认后，才能在同一事务中创建无登录凭据成员或标签。
导入成员不能跨来源合并，标签不能跨分类映射；已有同分类同名标签时禁止再创建重复项。

导入操作者是新旅行唯一 owner；备份中的其他成员获得 editor 权限。整个创建过程连同
可选基础资料、操作记录和初始完整快照在一个事务内提交。

## 强制不变量

1. ID 必须 URL 和文件名安全。
2. Day 日期唯一、有序且位于 Trip 范围内。
3. Day 只引用同 Trip Place；Segment 只连接其 Day 中的 Place。
4. 经纬度必须成对出现并在合法范围内。
5. 地点类型、费用类型和平台类型必须引用对应分类的标签。
6. 费用、物品和资料记录人的成员字段使用基础成员 ID，且成员已被当前旅行选择。
7. 普通业务接口中的物品读写只对其 owner 可见；完整快照与旅行备份仅按上一节记录的
   恢复和灾备例外授权。
8. Trip 概览中的物品数量和 Trip 操作记录中的物品内容只统计或返回当前成员的数据。
9. 写入成功但文件镜像失败时明确报告镜像待重试。
10. 相同幂等键与相同请求复用第一次结果；同键不同请求冲突。
11. 旅行备份的依赖清单必须与实际引用完全一致，校验和覆盖 Trip 状态和依赖描述。
12. 数据库已安装契约指纹必须与运行代码完全一致；不一致时健康检查失败。
13. 每次用户写事务回调都必须重新确认成员仍启用并具有所需 admin/Trip 角色；MongoDB
    自动重试不得复用事务外或上一轮回调的授权结果。
