# 手动创建旅行

这条流程适合从空数据库开始，完全通过 Web 页面创建一场旅行。它遵循当前唯一模型：
基础库保存跨旅行成员和标签；Trip 保存 Day、Place、Segment、预订、费用、物品和资料。

## 创建前准备

完成 [本地安装与首次管理员](getting-started.md#本机安装)，登录后先进入“基础资料”。

### 标签

至少准备：

- 一个或多个“地点类型”，例如景点、住宿、交通枢纽、餐饮。
- 一个或多个“费用类型”；预订类型直接复用这套类型，缺少任何费用类型时页面会阻止
  新增预订和费用。
- 平台类型。首次 bootstrap 会创建高德、飞猪、携程、小红书、12306 等常用平台预设，
  也可由管理员补充。

标签名称用于展示，记录实际保存稳定标签 ID。不要删除仍被地点、费用、预订或资料引用
的标签；页面会先显示影响范围。

### 成员

首个管理员本身已经是一个基础成员。其他同行者可在“基础资料 → 成员”创建：

- 只有显示名称：可以被旅行选择，但不能登录。
- 同时设置手机号和密码：可以登录，但仍需被具体 Trip 选择后才有旅行权限。

联系方式属于隐私数据，不要放进攻略正文、截图、Issue 或 Git。

## 1. 创建旅行骨架

进入“所有旅行”→“创建旅行”，填写：

- 旅行名称
- 开始日期
- 结束日期

系统会为日期范围内每天自动创建一个执行日，并跳到第一天。日期最多跨度 366 天。修改
旅行日期时，如果会排除已有执行日，系统会拒绝，先调整日程再修改范围。

## 2. 按天加入地点

在“今天”或“日程”打开一个执行日。旅行沙盘默认按旅行日期选择“规划”或“在途”模式；
手动切换会写入当前 URL，刷新后仍保留。规划地点时点击“整理地点”：

1. 选择已有地点，或点击加号新建地点并直接加入当天。
2. 新建时先选择地点类型；已配置高德时搜索候选，核对名称、地址、行政区和坐标。
3. 按大致游览顺序排列地点。这个顺序只是参考，现场可以随时改变。
4. 地点备注按需填写；只有酒店入住、车次、预约等确有硬约束时才补充大约到达/离开时间。
5. 保存地点清单。没有时间和交通段也属于完整、可使用的日程。

使用“整理地点”可以把已有地点关联到当天或改变顺序。Place 属于当前 Trip，不会进入
跨旅行基础库；同一 Place 可被多个 Day 引用。

验收：

- 当天想去的地点没有遗漏；顺序仅表示当前建议，不要求与现场执行完全一致。
- 经度、纬度成对填写，且没有颠倒。
- 六位天气 adcode 对应地点行政区。
- 导航链接是 `http` 或 `https`，能打开正确地点。

## 3. 按需补充交通

只有交通方式、换乘或耗时值得提前记录时，才在地点顺序之间点击“添加交通”或“再添加”：

- 起点、终点都必须属于该执行日。
- 方式可选步行、驾车、出租车、网约车、公交、火车、飞机、接驳车、景区车、轮渡、
  骑行或其他。
- 出发时间、估算时长、距离、导航链接和备注都可以留空。

Segment 描述的是两个 Place 之间如何行动，不替代地点顺序。改变地点顺序后要重新检查
已有交通参考是否仍合理；同一对相邻地点可以保存多种备选方式。反向或非相邻地点之间的
记录归入“其他交通参考”。不维护 Segment 不影响当天地点清单。

在规划模式点开地点，可直接添加关联预订和攻略，表单会预选当前地点、执行日和当前成员；
在途模式则集中显示高德导航、地点天气、订单链接、攻略摘要和当天物品。天气缺少行政区
代码、刷新失败或使用缓存时都会明确标注，不把旧数据伪装成实时结果。

## 4. 选择旅行成员

进入“成员”并从基础库选择同行者。创建者是 owner；其他选中成员通常作为 editor。
只有旅行成员才能成为费用支付人、分摊对象或资料记录人。物品按成员私有：普通 Web
新增和修改会由服务端把当前登录成员固定为所属成员，表单不能替他人选择或改变负责人；
需要每位登录成员分别维护自己的物品。

不要用显示名称作为关联依据；页面和 API 均使用稳定成员 ID。

删除同行成员时，页面先列出不能自动清理的预订、预订生成费用和资料。手工费用会显示
具体项目，个人物品只提示存在而不展示名称或数量。清空阻塞项后，可以在一次危险操作
确认中删除该成员、关联手工费用和个人物品；不确认级联时系统仍会拒绝删除。

## 5. 补充预订、费用、物品和资料

### 预订

填写项目、预订类型、预订人，以及可选地点、平台、日期时间、状态、链接和备注。状态：

- 待预订
- 已预订
- 已取消

新增预订会自动创建一笔关联的待登记费用；费用类型和支付人分别跟随预订类型和预订人，
不能在费用表单中修改。回到“费用”补充实际金额和冻结的分摊成员。删除预订时，页面会
说明关联待登记费用的处理范围。

### 费用

金额使用当前 Trip 币种展示，底层保存最小货币单位整数。选择费用类型、实际支付人、
`全部成员` 或 `指定成员` 分摊。系统根据已登记事实计算净额和最少转账建议。

### 物品

填写分类、数量和可选关联日；所属成员由服务端固定为当前登录成员，普通表单不显示或
接受负责人字段。各登录成员只能通过日常物品页面查看、修改和勾选自己的物品。证件号码、
药物病史等敏感原文不要写入普通备注，必要时只写行动提示。

### 资料

资料只保存标题、摘要内容、平台、记录成员及可选执行日/地点。把预约规则、限制、Plan B
和来源链接写清楚；不要整篇复制受版权保护的文章，也不要把社交平台 Cookie 放进内容。

## 6. 出发前检查

- 每天已收集想去的地点；已有 Segment 与当前建议顺序不冲突。
- 预约、开放时间、班次、天气和道路在临近出发时重新核验。
- 所有预订状态真实，未知价格和余票没有被标成已确认。
- 费用支付人和分摊成员完整。
- 各登录成员已分别检查自己的关键证件、药品、充电和天气装备。
- 每个高风险环节都有 Plan B 和退出条件。

## 7. 导出备份

在“所有旅行”中，只有 Trip owner 或管理员可对目标 Trip 执行“导出备份”；editor 和
viewer 无权导出。备份包含当前旅行全部业务状态、所有成员的私有物品及实际引用的成员/
标签描述，不包含密码、登录凭据、管理员身份、历史快照和操作记录。这是恢复和灾备例外，
不会扩大管理员或 owner 在普通物品页面查看他人物品的权限。

把备份保存到受限位置，不提交 Git。建议完成大规模修改、出发前和旅行结束后各导出一次。

若想复制为新旅行，选择“导入旅行”，上传备份，检查资源统计和校验和，完成成员/标签
映射后再确认。导入不会覆盖原 Trip，所有旅行内 ID 会重新生成。
